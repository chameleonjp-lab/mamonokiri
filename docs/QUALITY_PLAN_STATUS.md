## 第1段階の確認内容

変更前は64件の既存テストが成功。第1段階の変更後は、既存64件と追加25件の合計89件が成功した。型検査とPages用ビルドも成功した。

- タイトル滞在0・10・60秒、再挑戦で初敵の予告開始が一致。次の敵はその生成から自身の待ち時間を測る。
- 予告中に1,600ms中断しても、時間・体力・予告段階を保持して自動停止。700msの復帰猶予後に未処理の命中が1回だけ起きる。
- 手動停止・visibility・pagehide・pageshowを、進行中の飛刃を使って確認。停止中と復帰猶予中に命中しない。描画より先に入力が届いた場合も長い中断を検出する。
- 検査で使用した同条件では、30・60・120回/秒の更新で被弾回数・体力・得点・プレイ時間が一致。すべての戦闘入力や演出設定を保証する検査ではない。
- 描画エンジン生成失敗、シーン作成失敗、初回描画失敗、破棄後の遅い完了を検査。保存へのアクセスと容量不足を再現し、現在の設定を保持できることを確認。Reactの起動画面をHappy DOM上で描画し、準備完了前の開始抑止、失敗案内、再試行、名前保持を確認した。

既存の入力テストは、380ms実時間で待つ方式から通常の小さな更新を与える方式へ変更した。380msの単一中断は新仕様では自動停止となるため。即時ダメージがないことと通常更新で命中することの確認は維持し、飛刃が存在することも確認する。スマホ契約テスト内の時計の文字列確認は、新しい時計の呼び出しへ変更し、期限の保持を実際に検査するテストを追加した。

再試行の検査中、古いシーンの遅延した音処理が破棄後に残ることを確認したため、シーンが予約処理を管理し破棄時に解除するよう追加修正した。これは第1段階での記録であり、飛刃材質の再利用は第3段階で別途実装した。

## 第2段階の確認内容

今回の変更では、画面の幅と高さを戦闘ルールへ渡さないようにした。プレイヤーの左右の安定位置と敵の左右移動範囲を `-0.9`・`0.9` に固定し、回避中だけ中央を通過する。足元の3つの表示、強い予告線、攻撃範囲、左右攻撃の命中判定は、同じレーン間隔から計算する。狭い左右攻撃では中央を安全な通過位置として扱い、広域攻撃では中央も危険になる。

縦長画面ではカメラを少し遠ざけ、横長画面では基準距離を維持する。カメラの調整は表示だけに行い、プレイヤーと敵の座標・移動距離・命中判定は変えない。画面サイズ変更時にはカメラを再計算し、破棄時にリスナーを解除する。

- テストは既存89件から100件へ増加し、固定レーン、カメラ計算、予告線と3レーン表示、左右移動後の初回攻撃回避を追加した。
- `node --import tsx ../audit/projection.mts` を今回のコードで実行し、320×568、390×844、402×874、874×402の山伏頂点2,454点がすべて画面内に収まることを確認した。これは実機の見た目を保証するものではない。

## 第3段階の確認内容

反撃・防御崩し・大崩れへの強撃は、押下時にダメージを確定せず、攻撃開始時に記録した `startup` 後の共通命中時刻で解決する。通常斬撃は飛刃の到着を同じ予約時刻へ合わせる。ヒットエフェクトの強さによる短い停止処理は削除し、カメラ揺れだけを表示演出として残したため、演出設定で体力や命中結果が変わらない。

飛刃のメッシュは命中・再挑戦・敗北時に破棄し、材質は `flying_slash` をシーン内で共有する。スワイプは開始した `pointerId` だけが完了・取消でき、別の指やボタン操作が開始中のスワイプを奪わない。

- テストは第2段階の100件から103件へ増加した。通常斬撃の遅延命中、反撃の押下直後非ダメージ・命中時ダメージ、full/minimal演出での同一体力、飛刃材質が1つに留まること、開始指予約の契約を検査した。
- `corepack pnpm test`（103件）、`corepack pnpm check`、`git diff --check` は成功した。Pages用ビルドと頂点投影は第2段階から変更がないため、Draft PRの検査で再実行する。
- 実機の2本指・長押し・高速タップ・同時操作、全攻撃種のiPhone Safariでの体感、音・発熱・フレームレートは未確認である。

## 第4段階の確認内容

守備成功の得点は、受け流しと正しい回避を同じ敵の加点枠で数える。通常敵は3回、ボスは6回までで、上限後も受け流しの反撃受付、構え回復、正しい回避は動作する。結果画面には守備加点回数を残し、上限があることを表示する。

ランキングは旧`submit_score` / `get_best_score_ranking`を直接拡張せず、`supabase/migrations/20260911000000_mamonokiri_scoped_ranking.sql`の専用テーブル・RPCへ切り分ける。送信には勝負ごとのUUID、モード、難易度、`mamonokiri-score-v2`、乱数種、到達体数を含める。同じ勝負IDを再送した場合は既存結果を返し、別内容での使い回しは拒否する。旧共有ランキングの行は移行・削除しない。端末内の自己最高も得点規則版をキーへ含め、旧ローカル記録と比較しない。

送信失敗とランキング読込成功を別状態で表示し、失敗したスコアは結果画面に残す。再送ボタンは同じ勝負IDで実行する。新しい結果へ切り替わった後に前の通信が返っても、現在の結果を上書きしない。

- 守備加点の純粋な規則検査、実シーンで同じ敵へ5回受け流す検査を追加した。5回成功しても加点回数は3回、得点は780点で止まる。
- ランキング契約の条件付きpayload、上限付き読込、旧形式を含むレスポンス解析、同一勝負IDの重複応答を検査した。
- 起動画面の検査で、送信を503にしてもランキングの読込成功を別表示し、同じ結果を再送すると重複登録なしの応答を表示することを確認した。
- `supabase` CLIはこの作業環境にないため、migrationはPRに同梱して適用待ち。Supabase本番への適用とRPC実データの確認は、PRマージ後に担当者が行う。

## 第5段階の確認内容

タイトルの初期選択を「十番勝負・見習い」へ変更し、名前入力と「新しく始める」を最初の判断にした。勝負の長さ、難易度、片手配置・音量・演出・描画設定は「追加設定」に折りたたみ、必要な人だけ開ける。制作方法の説明より、予告を見て左右・防・斬を選ぶ遊び方を先に表示する。

「稽古を試す」は、最初の3体だけを使う独立した練習経路である。稽古中は見習い固定、体力3手順、端末内自己最高・オンラインランキングのどちらにも記録しない。左右回避と受け流し後の反撃を試せ、誤って被弾しても体力と構えを戻して同じ敵で再試行できる。稽古はタイトルから飛ばせ、結果から「正式な勝負へ」へ進め、後からタイトルで再開できる。

結果画面は、記録と統計の後に「直前の失敗」「次に試す」を置き、再挑戦を共有文・ランキングより先に配置した。正式勝負は「もう一度遊ぶ」「同じ敵順で再挑戦」「最初の画面へ戻る」、稽古は「稽古をもう一度」「正式な勝負へ」「最初の画面へ戻る」を表示する。失敗理由は空振り、回避方向、構え崩れ、直撃、途中離脱を戦闘側で保持する。

- 稽古の起動時に `practice=true`、`modeLimit=3`、見習い固定になることを実シーンで確認した。
- 稽古で危険線に残った場合も体力100・構え100を維持し、失敗理由と次の一手を状態へ残す検査を追加した。
- 起動画面で初期選択、稽古開始、結果の失敗理由、正式勝負への導線を確認し、稽古結果ではランキングRPCを呼ばないことを確認した。
- 全自動検査113件、`corepack pnpm check`、通常ビルド、Pages用ビルド、`git diff --check`が成功した。初見確認者5人中4人以上の成功率、CSSの実寸、Safariの見た目・音・発熱・FPSは実機で未確認である。

## 未確認と公開前の確認

確認用のブラウザからローカルの開発画面への接続が `ERR_BLOCKED_BY_CLIENT` で拒否された。今回の変更後の実画面は撮影・操作できていない。Reactの文書構造とイベントの検査は、CSS配置やWebGL表示の代わりにはならない。WebGLが使えるiPhone Safariでの確認は未完了として残す。

iPhone 17 Pro Safariで、準備中の開始抑止、正常な開始、名前・設定の維持、縦横のタイトルスクロール、停止後700msの復帰、ブラウザを離れて戻る操作を確認する。250msの自動停止が実機で頻発しないかも確認する。描画不可の再現が可能な検査環境では失敗案内と再試行も確認する。

mainへの直接push・マージ・公開はこの作業では行わない。Draft PRの自動検査と実機確認を分け、次の段階へ進む際は最新mainと未解決条件を照合する。

## 再現手順

```bash
corepack pnpm install --frozen-lockfile

corepack pnpm check
corepack pnpm exec vite build --base=/mamonokiri/
```

保存状態のReact連携は[React公式のuseSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore)の購読・解除・安定した状態値の条件に合わせた。起動画面の検査にのみ[Happy DOM](https://github.com/capricorn86/happy-dom)を開発用依存として追加し、ゲームの公開プログラムには含めない。
